# 签退机制（实测确认）

## 结论：签退是一个**独立活动**

`activelist` 里同时存在两类活动：

| `activeType` | 含义 |
|---|---|
| `2` | 签到 |
| `74` | **签退** |

一门课的真实时间线（Linux操作系统，2026-10-14）：

```
08:31  activeType=2   name='二维码签到'         ← 签到
09:55  activeType=74  name='二维码签到-签退'     ← 签退（独立活动）
```

**所以 `activeType=74` 必须和 `2` 一起收，否则签退会被完全忽略。**
官方 IM 的判断也是两者并列：`if (atype != 2 && atype != 74) return`。

## 签到活动里带着签退的预告

签到活动的 `getPPTActiveInfo` 会告知签退活动的存在：

```
签到 aid=1000000000001  activeType=2
     signOutId               = 1000000000002     ← 未来签退活动的 ID
     signOutPublishTimeStamp = 1791000000000     ← 签退的发布时间
     openSignOutFlag         = 1
```

也就是说**签退在发布之前就能预知**，可以用来做提醒。

## 签退活动的字段结构 = 签到活动的字段结构

```
签退 aid=1000000000002  activeType=74
     otherId      = 2             ← 类型相同（二维码）
     signCode     = '340924'      ← 同样返回
     ifRefreshEwm = 1             ← 同样是动态二维码
     ifNeedVCode  = 1
     openPreventCheatFlag = 1
```

`signDetail` 对签退活动返回的字段与签到**完全一致**（只在 `activeType` 上不同）。
**因此可以复用同一套签到分派逻辑，不需要单独实现签退。**

## 能否"当成签到一起操作"

**能合并成一个动作，但不能合并成一个请求。**

- 签退有自己的 `activeId` / `signCode` / `enc` → **必须各自提交**
- 前提是先签到成功（签退活动本身不校验，但业务上要先到）
- 所以正确做法是：**一次扫描、发现所有 `activeType ∈ {2,74}` 的活动、逐个签**

本项目的实现即为此：`SignEngine.findAllActive()` 收集全部，`signOneActivity()` 逐个提交。

## 顺带确认的风控规律

在 62 个真实活动上统计防作弊与图形验证码的关系：

| `openPreventCheatFlag` | `ifNeedVCode` 分布 |
|---|---|
| `0`（关闭） | `0` → **41/41（100%）** |
| `1`（开启） | `0` → 9，`1` → 12（**57% 要验证码**） |

**规律：关闭防作弊时必然不弹验证码；开启防作弊时超过一半会弹。**
所以可以读 `openPreventCheatFlag` 提前预测要不要人工滑一下。
